# D：单证交叉比对规则清单

文档版本：v0.4；状态：规则设计与评审草案，已实现人工样例、纯值比较和输入预检，正式规则引擎尚未接入。
契约基线：`722e56a`；工作分支：`feature/cross-check-quality`。

**D 已完成可独立推进的基础部分：**无歧义数值解析、g/kg 换算、明确参数下的比较、输入预检，以及人工样例和回归测试，见第 9、10 节。[D 阶段交接](d_handoff.md)列出可运行入口、具体契约需求和真实联调清单。正式字段适配、证据输出与完整 W3 仍待 A/C 对接。

## 1. 依据、范围和实现边界

- 开发约束以 [AI开发约束.md](../AI开发约束.md) 为准；目录遵循 [directory-structure.md](directory-structure.md)。
- 模型、枚举和序列化使用 [core/models.py](../core/models.py)；状态流转使用 [core/validators.py](../core/validators.py)，结合 [contracts.md](contracts.md) 阅读。代码中的已有行为与文档中的目标要求分开记录。
- D 的实现目录为 `validation/`、`tests/`；本轮实现人工测试样例和纯 Python 核心。已有 `main.py`、`utils/` 等旧实现不作为新功能入口。
- 首批开发 P0：商业发票与装箱单、Case 基础信息与各份适用单据。P1：发票与合同、装箱单与提单；属于规则范围，但启用前需要 C 的字段样例和业务口径。
- 规则使用确定性 Python 逻辑，不调用模型裁决。人工构造样例可先行，不等待完整解析界面；完整 W3 验收需要 C 的解析与复核模块。
- 本清单不新增公共模型、正式字段命名、OCR、上传页面或法规认定功能。公共契约不足时先向 A 提出变更，不用自定义字典或特殊字符串绕过。

## 2. 已有公共契约与待补能力

### 2.1 直接复用的类型

| 用途 | 当前契约 | 使用要求 |
|---|---|---|
| Case 基础信息 | `Case.case_id`、`order_no`、`customer_name`、`destination_country` | Case 字段与单据字段的对应语义需 C 确认 |
| 必需单据 | `Case.required_document_types`、`Document.document_type` | 不凭上传顺序猜测文档类型；同类型多份单据的选择规则需确认 |
| 文档与版本 | `Document.document_id`、`case_id`、`current_version_id`；`DocumentVersion.version_id`、`fields` | 检查归属，使用指定的当前版本，不根据文件名或更新时间猜版本 |
| 字段与来源 | `ExtractedField.name`、`value`、`normalized_value`、`status`、`page_number`、`sheet_name`、`cell_reference` | 来源位置随字段保留；不能假定 `value` 已代表最终人工确认值，其取值约定需 C 明确 |
| 字段复核 | `FieldValueStatus.CONFIRMED` 等 | `CANDIDATE`、`REJECTED`、`MISSING` 不作为已确认字段使用 |
| 比对结果 | `CrossCheckResult` | 使用现有 `rule_code`、`rule_version`、两侧文档/字段/值/来源等字段 |
| 风险 | `RiskItem`、`RiskSeverity.BLOCKING`、`blocking` | 失败或待复核的必要规则建议使用阻断风险；风险与结果的关联方式需 A 确认 |

| 业务显示名称 | 代码枚举 | 序列化值 |
|---|---|---|
| `PASS` | `CrossCheckStatus.PASS` | `pass` |
| `FAIL` | `CrossCheckStatus.FAIL` | `fail` |
| `PENDING_REVIEW` | `CrossCheckStatus.PENDING_REVIEW` | `pending_review` |

正式对象使用枚举，JSON 等序列化使用 `core.models.to_dict`，不把大写显示名称当作枚举值。

### 2.2 当前缺口：作为对接事项，不宣称已经支持

1. `CrossCheckResult` 没有独立的两侧文档版本 ID、规范化值、严重级别或必要规则标记。现有 `left_source` / `right_source` 是来源说明字符串，不能自行塞入特殊格式来代替缺失的结构化契约。由 A 确认最小扩展及风险关联方案。
2. `ExtractedField` 尚无专门的单位、币种、商品行标识、配对关系字段。由 A/C 明确如何用公共契约表达；不能临时约定 `value` 内的匿名结构。
3. 机器原值、人工改值、最终确认值的读取方式，以及 Case 字段自身的确认依据和来源，仍需 C 说明；不能由 D 从 `source` 或 `note` 猜测。
4. 当前状态校验会检查必需单据类型、当前版本及其中已有字段的确认状态；通过/关闭时要求复核任务非空、必需任务已批准、比对结果非空且传入结果全部为 `PASS`。
5. 当前状态校验尚未验证必要规则是否全部产生结果、结果是否属于当前 Case / 当前文档版本，也未列举每种单据必须存在的字段。不能把“传入的一条结果通过”解释为“全部必要规则通过”。完整性、归属和旧结果失效机制需要 A/C/D 联调。

## 3. 共同判定要求

### 3.1 单条规则的执行顺序

按下表顺序检查；任一步无法建立比较前提，就记录具体原因并停止该条比较。其他独立规则继续执行，不能因一条待复核而丢掉其余结果。

| 顺序 | 检查内容 | 未满足时的处理 |
|---|---|---|
| 1 | 规则是否适用、是否必要、应检查哪些单据和商品 | 适用范围未确认时不能形成全部通过结论；已明确不适用的规则记录原因，不生成假通过 |
| 2 | 文档是否属于当前 Case，指定版本是否存在且为当前版本 | 缺少文档或版本依据时待复核；其他 Case / 旧版本的输入或结果不得参与本次通过判断，错误处理复用公共契约 |
| 3 | 必要字段是否存在、已确认，最终确认值和来源是否可读 | 待复核，明确哪一侧缺少哪个字段或确认依据；值相同也不能跳过此检查 |
| 4 | 数值格式是否合法，单位、币种、角色、统计范围及商品配对是否明确 | 待复核；保留原值和具体原因，不先转换再猜语义 |
| 5 | 规范化和比较策略是否明确，值是否合法 | 待复核；不得用两侧相等掩盖非法输入 |
| 6 | 按明确策略比较并生成证据 | 一致为 `PASS`，确定不一致为 `FAIL`；证据表达受第 2.2 节契约缺口约束 |

程序异常不伪装成业务 `FAIL` 或 `PASS`；调用现有公共错误处理路径，且本次检查不得据此被认定为完成。此表描述目标行为，不表示正式入口已实现。

### 3.2 结果粒度与完整性

- 按 Case、规则、选定的单据对及其当前版本、比较范围分别产生结果；明细规则还需区分已配对商品。该粒度是待对齐的需求，不自行新增公共复合键或私有协议。
- 同一规则可能有多条结果：例如 CASE-003 检查三份适用单据应有三份对应结论；IP-002 检查两个已配对商品应保留两条明细。不能仅按 `rule_code` 覆盖前一条。
- 在运行前确定应检查的范围，运行后核对应有结果与实际结果。未匹配商品、缺失字段和缺失结果都要显式暴露；不能只汇总成功匹配的部分。
- 当前版本不变但最终确认值或规则版本改变，也需要重跑；`checked_at` 本身不能证明结果仍然有效。输入变更与旧结果失效的接入见 Q-08。

### 3.3 共同通过条件

1. 先明确 Case 适用的规则集合和必要规则。P0/P1 是开发顺序，不等于自动启用；缺少适用范围时不得报告全部通过。
2. 已启用的必要规则缺少文档、字段、来源、复核依据或比较口径时返回 `PENDING_REVIEW`。未启用规则记录适用范围说明，不伪造 `PASS`，空结果集合不算通过。
3. 使用同一 Case 的文档和正确版本；总计对总计、明细对已确认配对的明细。不得把单据级重量、箱数按商品行重复累加。
4. 商品需要唯一且已确认的标识或人工配对。行序不同不代表商品不同；重复标识、缺少配对、拆分/合并行口径不明时待复核，不按行号、模糊品名或模型语义自动配对。
5. `PASS`：规则适用，必要输入与复核证据齐全，比较策略明确，满足一致条件。`FAIL`：比较前提明确且确定不一致。`PENDING_REVIEW`：不能可靠判断，必须说明原因。
6. 同时存在失败和待复核时保留全部明细；汇总方式与 A 对齐。首批启用规则是否均为必要规则，待评审确认。
7. 所有必要规则通过只是 Case 通过/关闭的必要条件，其他复核和状态条件仍由公共状态校验及 C 的流程检查。

## 4. 规范化规则

| 类型 | 首版处理要求 | 待复核情况 |
|---|---|---|
| 金额 | 从明确的数值文本解析为 `Decimal`；同时核对币种和金额范围；不使用浮点数作最终比较，不做汇率换算 | 数字分隔符、币种、税费/运费范围、精度或舍入口径不明 |
| 数量 | 保留数值、单位和商品范围；不截断小数，不跨商品直接求和 | 单位、数量合法性、拆分/合并行口径不明 |
| 箱数/件数 | 区分箱、包、托盘和商品件数；整数数值形式可统一，不能把 `10.5` 截为 `10` | 包装层级或装箱系数不明、非整数计数无法解释 |
| 重量 | `Decimal`；先明确支持 `g`、`kg`，按 `1 kg = 1000 g` 精确换算；毛重、净重分开 | 单位缺失或不支持、重量类型/统计范围不明、比较策略缺失 |
| 币种 | 已确认的币种代码统一大小写，别名仅按明确映射处理 | `$` 等有歧义符号或币种缺失，不继承另一侧币种 |
| 日期 | 接受有效的 `YYYY-MM-DD`；其他格式需要明确约定；首版不因此新增日期比对业务规则 | 无效日历日期或 `01/02/2026` 等格式歧义 |
| 单位 | 与数值一起比较；只做明确换算或已确认别名映射 | 无单位不能默认补齐；箱与件没有产品装箱系数时不换算 |
| 文本/标识 | 去除首尾空白，保留有意义的内部字符、标点、前导零；使用已确认标识或映射 | 不自动翻译、改写公司/品名，大小写和别名规则不明时待复核 |

- 区分数值 `0`、空文本、`None` 和格式错误。`NA`、`N/A`、`—` 等文本按契约解释，未约定时保留原值并待复核。
- 零值、负值、小数数量是否合法需要按字段确认；不能让两侧相同的非法值通过。当前 `validate_case` 已禁止负的 `Case.invoice_total`，不得在新规则中放宽。
- 精度、舍入与容差分别确认；不自行加默认误差或四舍五入。缺少业务比较策略时相关规则待复核，纯转换函数仍可独立测试。
- 数值入口不接受布尔值、`NaN`、正负无穷；不把二进制浮点数直接转成业务精确值。浮点输入应由上游提供可追溯的十进制文本或经确认的转换口径；科学计数法、千位符和小数分隔符未约定时待复核。

首版建议仅支持显式给定的非负绝对容差：两侧语义一致并换算到同一单位后，令 `delta = abs(left - right)`，`delta <= tolerance` 为通过，超过为冲突。金额还须币种相同。边界包含等号，容差与数值均使用有限 `Decimal`；容差无效时不能执行比较。此策略待 Q-05 确认，测试可先用显式参数验证，不设生产默认值，也不提前加入相对误差或汇率换算。

## 5. 业务规则目录

以下示例全是人工构造的测试数据。假设共同前提已满足，角色/标识/单位已确认；金额和重量样例显式采用精确比较（容差为 0），不代表生产容差已获批准。每条规则至少准备 `<规则ID>-PASS`、`<规则ID>-FAIL` 两个基础用例，以及适用的缺失和格式异常用例。

每条规则实现前还须明确：适用单据及字段映射、比较层级（总计或商品明细）、合法值、比较策略、来源与确认依据。明确采用字面比较时，确认后的名称不同可以判冲突；只有角色、别名或映射仍不明确时才待复核，不能把所有名称差异都退回人工。

P0 规则是否必要需按 Q-01 确认。例如发票模板没有箱数，不得自动关闭 IP-003 来取得通过；先确认该规则是否适用，适用但字段缺失则待复核。P1 尚未启用时保留范围说明；启用后同样不能跳过缺失输入。

## 6. 边界、契约和集成测试要求

这是完整目标清单；部分值级行为已有测试，第 9 节记录实际覆盖范围。文档版本、来源证据和完整 W3 的集成要求仍待接入，不能据此宣称全部验收完成。

| 用例 ID | 输入或操作 | 预期 |
|---|---|---|
| EDGE-001 | 已启用必要规则缺少文档或任一侧字段 | 待复核，指出缺少哪一侧、哪个字段；不补 0 |
| EDGE-002 | 数值为 `abc`、歧义分隔符、不允许的值 | 待复核，保留原值；不截断、不取绝对值 |
| EDGE-003 | 同一重量字段为 `1 kg` 与 `1000 g`，比较策略明确 | 通过；保留原单位与换算证据 |

## 9. 已交付的人工样例和纯 Python 核心

### 9.1 文件与能力

| 文件 | 本轮交付 |
|---|---|
| [cross_check_cases.json](../tests/fixtures/cross_check_cases.json) | 41 个人工构造样例，预期状态与原因手工填写；通过 `synthetic` 标明测试用途，profile 只用于减少测试重复，不是跨模块接口 |
| [normalizers.py](../validation/normalizers.py) | 十进制数、文本、币种代码格式、有效 ISO 日期的规范化，以及 g/kg 双向精确换算 |
| [rules.py](../validation/rules.py) | 数量/包装计数、重量、金额、币种、文本的纯比较，返回 `CrossCheckStatus` |
| [test_normalizers.py](../tests/test_normalizers.py) | 缺失/空值/非法格式区分、零值、日期、单位和精度测试 |
| [test_rules.py](../tests/test_rules.py) | 人工样例、双侧复核门槛、容差边界、未知配置及高精度测试；样例循环禁用 socket 验证离线运行 |

支持 `Decimal`、整数和首尾可带空白的普通十进制数文本，例如 `100`、`+100.00`、`-10.5`。规范化函数只转换格式；负数、零值、小数在业务上是否合法由比较时显式给定的策略决定。数值比较首版仅支持非负下限，不支持负数业务值。拒绝布尔值、浮点数、非有限数、千位符、科学计数法、文本占位符和未知单位；保留原输入由调用方负责，函数不修改输入。

重量仅支持精确代码 `g`、`kg`，不猜测 `KG`、`lb` 等别名。币种仅统一三字母代码格式与大小写，不验证完整货币名录；代码身份由调用方确认，不从 `$` 推断。日期支持有效 `YYYY-MM-DD`，未新增日期业务规则。

### 9.2 调用前提和错误处理

- 每个比较函数都要求两侧 `FieldValueStatus.CONFIRMED`，并显式设置 `context_confirmed=True`。后者表示适用性、最终值选择、角色、商品配对、范围与比较口径已经确定；未提供则待复核。这些参数仅服务于准备好的值，不替代人工复核记录。
- 数量需显式给出两侧相同单位、非负 `Decimal minimum`、`allow_fractional`。箱/件单位不同则待复核，不提供默认装箱系数，不自动匹配商品行。
- 重量和金额需显式给出非负 `Decimal minimum` 与 `tolerance`；未配置返回待复核。重量下限和容差均以 kg 为单位；金额使用同一币种单位，不舍入、不换汇。差值等于容差可通过，样例中的零容差和 `0.01` 均非生产默认值。
- 文本比较仅在已确认字面规则下去首尾空白，保留大小写、内部空白、标点和前导零；别名/角色未定时不应将 `context_confirmed` 设为真。
- 规范化错误使用现有 `ValidationError`，`details.reason` 区分缺失、空文本、非法格式等。比较函数将无法比较的输入映射为 `PENDING_REVIEW`；配置为负数、非有限数或错误类型时直接抛出 `ValidationError`，不得将异常当作检查完成。

纯函数仅给出值级状态，不读取 `ExtractedField.value` 或 `normalized_value`，不产生正式 `CrossCheckResult`。待复核原因、两侧原值、规则 ID、来源和文档版本将由后续适配层结合公共契约输出；当前不能将纯函数的 `PASS` 直接用于 Case 通过/关闭。复用的公共契约为 `CrossCheckStatus`、`FieldValueStatus`、`ValidationError`；没有修改 `core/`、状态流转或增加依赖。
