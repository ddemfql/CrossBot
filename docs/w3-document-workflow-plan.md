# W3 外贸交易与单证工作台计划

## 目标

把 W3 从单据解析示例扩展为案件级工作台：围绕一笔交易管理业务资料、单据原件与版本、结构化字段、复核和跨单据检查，并从已确认的数据生成可控的业务文件。近期以“订单/PI → 出货单据 → 已发货待收款”的闭环作为主演示；后续再按业务需要扩展其他贸易类型。

W3 不应把 AI 输出当作业务事实。金额、数量、日期、状态和跨单据一致性由结构化数据、人工确认和确定性规则控制；模型只能协助理解/起草，不能批准 Case、签发文件或代替报关主体申报。

平台面向多个环节的业务员共同使用：各岗位应能查看交易上下文和已形成的资料，在授权范围内补充或修改自己负责的内容，并把任务交接给下一环节。关键业务批准必须由可识别的真人执行，批准记录绑定当时的资料/生成文件版本并进入审计历史。页面按业务任务和熟悉的单据组织，让一般业务员无需理解技术配置即可完成工作。

## 依据与设计原则

- 用户提供的 `credit-egg-platform` 适合借鉴其架构原则：原始文件只读、原始/标准化/显示数据分层、配置驱动规则、人工审核状态机、模板版本、生成记录、文件哈希和审计日志。只借鉴原则，不复制其 NocoBase/Carbone 等技术栈或学分业务模型。
- 用户给出的发货资料包显示，单笔交易可能同时有 PI 和修订版、买方 PO 和修订版、销售合同、产品规格/图片、商业发票与装箱单、ISF、提单、Prop 65/TSCA 声明和出货照片；资料含 PDF、旧 `.xls`、`.xlsx`、`.docx`、JPG 等格式。
- 参考文件可能含真实客户和交易信息。不得把原 ZIP、客户/订单标识、原始表格或未脱敏字段提交到代码库；自动化测试使用合成或充分匿名化数据。
- 官方资料确认出口单证、付款方式和 Incoterms 会影响流程要求；美国 ISF、承运人提单、法规声明都有各自责任方，不能假定由出口商系统统一生成或提交。适用文件清单必须按国家/地区、产品、运输方式、Incoterm、付款条款和交易角色配置。

## 交易流程模型

以可配置里程碑表达常见流程，而不是强制每单走完全相同的状态：

1. 询盘与报价：需求、报价版本、有效期、币种、贸易条款和待确认项。
2. 订单确认：买方 PO、销售合同、PI/付款节点；保存修订版并比较数量、价格、币种、交期等变化。
3. 产品准备：规格、包装、标签/Artwork、产品图片、客户或市场要求的合规材料。
4. 生产与放行：生产/检验资料、出货数量和包装数据；可按当前项目范围延后实现。
5. 出运准备：商业发票、装箱单、Shipping Instruction 及按交易条件需要的出口资料；复核后才作为正式业务输出。
6. 运输与清关：托管货代/承运人/报关代理提供的单据和回执，记录责任方、时间和状态。
7. 收款与归档：按预付款、赊账、托收或信用证等约定追踪应收金额、到期日、收款记录和未结余额。

每个里程碑应有负责岗位/人员、待办、可执行操作、交接条件和完成记录。销售、跟单/采购、单证、出货/物流、财务等岗位围绕同一 Case 协作；跨岗位可查看必要上下文，写入权限按字段、单据或流程动作配置。业务更正需填写原因并记录修改前后值；若变更影响已生成或已批准文件，应将受影响产物标记为过期/需重审，不能让旧批准继续覆盖新内容。

交易里程碑、文档状态和收款状态是不同维度。现有 `CaseStatus` 用于 Case 处理流程，不能把 `passed` 解释为“已发货/已收款”；新增交易/应收状态前先与 `core/` 对齐公共模型。

## 文件能力分类

| 能力 | 文件示例 | 系统行为 |
|---|---|---|
| 可由卖方业务数据生成的草稿 | 报价单、PI、商业发票、装箱单、Shipping Instruction | 从已确认的交易快照和版本化模板生成；提供预览、校验、人工批准和下载 |
| 外部收到/双方签署后托管 | 买方 PO、销售合同签署版、提单、检测报告、Prop 65/TSCA 等合规文件、货运照片 | 上传原件，分类、关联交易/产品、记录签发方/版本/日期/有效期；不得改写原件 |
| 由授权主体提交/签发 | ISF/报关资料、承运人最终提单、需签字的合规声明 | 可整理字段或生成待审草稿/数据包；记录实际提交人、签发人和回执，服务不能伪造签名、证书或提交成功状态 |

文件托管与文件解析分开设计：首版可接受并安全保存 ZIP 示例中的 PDF、`.xls`、`.xlsx`、`.docx` 和图片；只有明确支持的格式/模板才提取结构化字段。`.xls` 兼容、扫描件 OCR、任意版式文档解析分别评估依赖、准确率和成本，不因文件可上传就宣称已解析。

## 实施阶段

### 1. 定义交易数据与跨模块接口

- 与 `core/` 确认交易主数据模型：买卖双方、订单号、目的地、产品/行项目、数量及单位、币种、付款条件、Incoterm 及版本、运输方式、预计/实际日期和里程碑。
- 与 `storage/` 确认原始文件、文档元数据、版本、模板、生成记录和审计事件的持久化/读取 API。
- 与 `validation/` 确认标准化字段、规则编号、差异证据和 `PASS` / `FAIL` / `PENDING_REVIEW` 契约。
- 与模板/渲染实现负责人确认可用格式和渲染服务接口；W3 负责编排和业务校验，不把渲染或规则副本塞进页面层。
- 与身份/权限实现负责人确认岗位、用户、字段/动作权限，以及审批记录如何绑定具体数据和文件版本；审批接口不得接受模型或系统任务作为批准人。
- 对公共数据模型变更一次集中提出并测试，随后再拆分并行任务；Case、解析/文档仓储、模板渲染和测试可在接口稳定后由多个子代理并行负责，避免多人编辑共享契约或同一文件。

### 2. 建立交易 Case 和文件工作区

- 创建交易 Case、参与方、产品/行项目、必需文档配置和事件时间线。
- 上传原件时记录 SHA-256、原始文件名、MIME/扩展名、大小、上传人、时间、来源方和文档类型；原件不可覆盖，重传形成新版本并可标记 superseded。
- 文档可关联到 Case、订单、产品、出货批次、付款节点或其他文档；可按类型、状态、责任人、到期日检索。
- 允许对无解析器文件进行存储、预览/下载、标签和版本管理。文件路径和下载接口需防路径穿越；文件名不能直接作为存储路径。
- 以“我的待办/待我复核/等待对方/已完成”等业务任务视图支持岗位交接；详情页用时间线显示谁在何时完成了什么、当前由谁处理及下一步需要什么。
- 权限要同时约束查看、编辑、复核、批准、下载和导出；多人协作时保留变更记录，避免未经授权的角色修改已批准字段。

### 3. 形成可复核的交易主数据

- 从 PO、PI、规格表等受支持来源提取候选字段，保留文件版本和页码/工作表/单元格等来源定位。
- 机器候选、规范化值、人工确认值分层保存；修订文件展示字段差异，不静默覆盖已确认订单数据。
- 低置信度、冲突、缺失字段形成待复核项；记录修改前后值、操作者、时间和理由。
- 第一阶段只解析固定模板/明确测试过的文本 PDF 与 Excel。旧 `.xls` 可先原件托管，解析适配作为独立子任务验证后加入。

### 4. 生成首批卖方文件

- 首先生成 PI、商业发票和装箱单草稿，数据来自已确认交易/出货快照；报价与 Shipping Instruction 作为随后扩展。
- 模板按文档类型和版本管理，保存模板哈希、字段映射、规则版本和适用条件；模板变量由结构化显示数据填充，不让模板承担业务计算。
- 每次生成记录输入数据版本、模板版本、操作者、时间、输出格式、产物哈希和生成后校验结果。重新生成创建新的产物版本，不覆盖前版。
- 生成后执行确定性校验：必要字段齐全、金额/数量计算一致、CI 与 PL 的约定字段一致、模板无未替换变量；不通过时只给预览/待修正状态，不可标为正式。
- 正式输出前由授权人员复核。批准动作由已登录的人类用户主动完成，记录用户身份、时间、批准意见、输入数据版本、文件版本及文件哈希；AI、后台任务和自动规则只能提出待办或校验结果，不能代点批准。
- 批准后的文件若因源数据、模板或内容变化而重新生成，旧批准仅对旧版本有效，新版本必须重新走人工复核/批准。若业务要求具备法律效力的电子签名，另行接入获认可的签署服务或线下签署流程；普通“批准”记录不得宣称等同于法定电子签名。
- 生成记录应能回溯到输入字段及来源，便于处理 PO/PI 后续修订。

### 5. 多岗位审批与易用界面

- 配置岗位和动作矩阵，至少覆盖销售/报价、订单跟进、单证、出货/物流、财务及复核/批准角色。每个岗位只需看到当前任务所需的字段、文件和历史；共享查看不自动意味着可编辑或批准。
- 支持逐环节提交、退回补充、转交、复核、批准和关闭；批准人必须是具名、已认证的人类用户，记录批准理由、时间、所批准的资料快照/版本及对应文件哈希。关键审批不得由 AI、定时任务或系统账号完成。
- 界面使用业务员熟悉的“订单、客户、产品、单据、待办、待确认、已批准”等词语；把流程呈现为当前环节、所需资料、缺项/风险、负责人和下一步操作，避免暴露 JSON、内部规则码或模型提示词作为日常工作入口。
- 对常见操作提供明确表单、合理默认值、字段说明、校验错误和修订对比；不要求用户手工维护技术配置或理解文档解析细节。复杂字段来源和审计信息可按需展开查看。
- 关键字段或已批准资料被修改时，明确告知影响范围并自动退回相关环节重审；保留旧版和旧签批，不能静默沿用。
- 用代表性业务员完成典型任务走查：创建/接手订单、修订数量、复核 PI 或 CI/PL、退回缺项、批准一个固定版本并交接到下一岗位；记录卡点并据此调整文案和步骤。

### 6. 管理运输、合规附件与收款

- 记录出货批次、订舱/装运节点、ETD/ETA、货代与承运人、提单号、最终单证和外部回执；用事件记录状态变化。
- ISF 等特定进口申报按目的市场和责任方配置。美国海运 ISF 通常由进口商或其授权代理提交；CrossBot 只管理出口方提供的数据和收到的回执，不默认代报。
- 记录付款条款、发票/应收金额、币种、到期日、部分/全部收款及凭证，提供逾期和待跟进队列；催款消息先生成草稿，由用户发送。
- 产品合规文件需要按市场、产品、签发机构、适用范围和有效期管理；Prop 65/TSCA 等声明不能泛化成 AI 自动认证。

### 7. 端到端验证与扩展

- 用完全合成的数据构建一条示例交易：PO 修订 → PI → 产品/合规附件 → CI/PL 草稿 → 外部提单/ISF 回执托管 → 已发货待收款。
- 覆盖重复上传、版本替代、解析失败、字段不匹配、模板缺项、渲染失败、生成后规则失败、部分收款和文件过期等场景。
- 覆盖岗位权限矩阵、跨环节修改审计、无权限编辑/批准被拒绝、AI/系统账号无法批准、批准后版本变化触发重审等场景。
- 让代表性业务员在少量指导下完成上述典型任务，确认页面中的岗位词汇、待办、缺项说明和下一步操作足够直观；把易用性检查纳入交付验收，而非留作视觉 polish。
- 对真实 ZIP 只做本地人工验证或在明确隔离的环境验证；不将原始文件、客户名称、订单号、地址、联系人或签名写入测试、日志、截图和提交记录。
- 运行 W3 与公共契约相关测试、格式/语法检查和生成文件冒烟测试，交接改动、接口版本、测试结果、限制和待办。

## 首期范围与非目标

首期优先做交易 Case、通用文件版本管理、订单/PI 修订追踪、确定性字段校验，以及 PI/商业发票/装箱单草稿的可追溯生成；同时具备最小岗位待办、授权编辑/复核、真人批准和版本绑定审计。以“已发货待收款”作为演示终点。按阶段扩展提单、ISF、合规附件与应收跟进。

不在首期内：自动邮件/自动催款、直接向海关或承运人提交、AI 自动审批、自动签署或生成法定证书、扫描件 OCR 的全面支持、全行业规则库、强制所有订单使用同一套文件清单。

## 验收条件

- 一笔交易能关联原始文件、修订版、结构化确认值、生成草稿、外部正式文件和收款记录。
- 同一字段能追溯到机器来源或人工修改记录；同一产物能追溯到输入数据版本、模板版本及输出 SHA-256。
- 新版本和重新生成都不覆盖原文件或先前产物。
- CI/PL 等跨文件冲突、未复核关键字段或规则待定时，不会错误地标记正式通过。
- 外部签发/签署/申报文件明确显示责任方和来源，不会被误认为系统生成。
- 至少两个业务岗位可在授权范围内查看、修改并交接同一交易；越权编辑和非人类批准会被拒绝并留有审计证据。
- 批准可追溯到具名人类用户、时间、意见、当时数据版本和文件哈希；批准后内容变化会触发重新复核。
- 代表性业务员能够依照页面提示完成核心路径，无需编辑配置文件或理解内部技术字段；易用性走查发现的问题已处理或列明。
- 首期端到端样例和相关测试通过；不把示例 ZIP 中的真实交易资料提交到仓库。
