# 第十步：英文付款表达检查

日期：2026-10-29。用户已回复“第十步通过”，确认下面的示例练习通过；新版本 C03 生成/导出的用户实测文件尚未取得，相关功能目前有离线测试证据。

## 做什么

本地规则 C03 在英文句子中寻找付款词及 agreed / accepted / confirmed / approved / agreement 等确认词。出现直接肯定表述时，标记为可能误写，展示原句、中文批注和待双方确认的建议表达。带否定、疑问、条件等限定词时转人工判断。没有命中也不表示通过，更不代表合规或双方已经同意。

这不是大模型语义审核，只是有限短语筛查。可能漏检同义表达、跨句指代，也可能标记合理的历史陈述。输入中即使写了“双方已同意”，应用也没有验证交易双方身份与接受证据，仍需人工复核。

## 来源与类别纠正

运行时读取 `local_lab/rules/payment-wording.json`，保存规则版本、来源、依据与边界。判断依据是本应用的数据事实：payment_status=provided 只表示已填写，并没有双方接受的证据字段。

背景参考：[联合国 UNCITRAL 第18条摘要（2004）](https://digitallibrary.un.org/record/535327/files/A_CN.9_SER.C_DIGEST_CISG_18-EN.pdf)。第18条涉及接受要约的意思表示/行为；沉默本身不等同于接受。2026-10-29 搜索工具取得官方文档第18条摘录，直接打开 PDF 返回403；未声称读完整摘要或判定具体交易适用。公约适用、行为接受和交易习惯均不在本功能判断范围。

本地筛查逻辑为项目自定义，不是该条文规定的字符串规则。**C03 与 C02 都围绕合同条款；不能把它们当成比赛要求的两个类别。** 先前助手将本功能称作第二类校验不准确，已纠正。另一类别仍待补齐。

## 本次用户只做一个练习（零 API 调用）

1. 找到“第十步：检查英文是否把待确认写成已同意”。
2. 点击“填入误写示例”，再点“检查这段英文（不调用 AI）”。应显示可能误写、原句及修改建议。
3. 点击“填入待确认示例”，再次检查。练习结果应变为“未发现明确肯定表述，仍需人工审核”，不显示绿色批准。

两句分别是：

```text
The payment terms have been agreed by both parties.
The proposed payment terms remain subject to confirmation by both parties.
```

第一句说双方已经同意，第二句保留待确认。练习不改报价/历史，不生成模型草稿，也不要求重新输入密钥。练习报告可下载独立 JSON。修改英文或付款条件后旧练习结果失效，需重新检查。

## 与真实草稿的关系

成功生成新草稿后，程序检查其英文原文，将报告放进该版本 `wording_report`；不把生成后的检查冒充生成前输入。不自动修订模型原文。TXT/全部版本 JSON 包含报告。历史旧版本未保存则明确提示，不事后伪造生成时检查。练习结果与真实版本结果分开显示和保存。
