# 根据需求访谈调整的参赛与学习方案

日期：2026-10-27。性质：助手在逐题访谈后形成的最终推荐方案；已确认目标和协作方式不等于用户已确认每项产品细节。后续不应重复询问已回答的偏好。

## 用户已经明确的需求

- 洪彬斌，单人参赛。
- 主要目标：独立完成可运行作品、学会借助 AI 开发；获奖不是目前声明的首要目标。
- 能运行和修改简单代码，曾在 AI 辅助下完成水果类 2048 微信小游戏。
- 选题、任务拆分、读代码、调试与收尾都遇到过困难。
- 第一层完成标准：自己能运行、修改并讲清主要流程；第二层目标：逐渐理解主要代码并继续开发。
- 外贸基础基本为零，选择出海赛道主要因为觉得另一个赛道更难。
- 希望助手按“容易做完、容易演示、能学到东西”推荐明确方向。
- 采用逐步教学：一次完成一个小功能，助手解释，用户运行验证，再推进。
- 每次只问一个问题，并附建议与理由。
- 尽量零新增费用；首版在自己的电脑运行和现场展示，不要求公网部署。
- 暂无客户或业务资料，用公开资料与明确标注的模拟案例。
- 愿意尽力投入时间，但没有承诺固定每日小时数。
- 模型接口留待之后配置，不反复追问凭证。

## 推荐作品：询盘与报价小助手

给完全不熟悉外贸的人解释：买家说“我想买什么、多少、有什么要求”，这就是询盘。卖家核对产品资料，再回复价格和交货等条件，就是报价。买家改变数量后，需要重新核价并确认其他条件有没有变化。

作品帮助业务员完成这条小流程。首版用虚构布袋商品，不做全行业系统。面向外贸业务员输出客户回复与报价草稿；面向采购/跟单人员输出中文核对清单。真实需求和客户价值仍未经过访谈验证。

示例：买家想买 300 个布袋，某些条件缺失。应用查目录、指出待确认项；用户补充后生成草稿。买家把数量改成 1000 个并要求提前发货，应用按模拟价格档位重算、展示变化并提示待确认交期。不能把备货时间等同于承诺到货时间。

### 首版界面与范围

1. 输入区：选一款商品、粘贴询盘、补充缺项。
2. 结果区：英文客户回复、货品报价表、中文采购/跟单核对单。
3. 反馈区：风险标记、文字批注、修改前后对比。
4. 下载：保存草稿与核对结果，所有模拟内容带标签。

没有平台登录/自动发信、客户爬取、完整 CRM、支付、图片生成或公网部署。两条业务工作流仍是首次 RFQ 回复与邮件议价修订；不是平台自动化。

与较早 product-direction.md 的差异：首版优先通过“业务员与采购/跟单两类角色输出”满足产出覆盖要求，英文客户回复+中文内部清单；不把西班牙语当首版必做。旧数据 T11 的西语样例保留为扩展项，不纳入当前最小验收集；两轮对话、两类业务检查、两个目标场景都仍必需。

## 如何兼顾比赛要求

| 要求 | 计划实现 |
|---|---|
| 两类角色/场景的本地化业务产出 | 业务员的英文客户回复与报价；采购/跟单的中文确认清单，分别适配对外与对内任务 |
| 两个目标平台或场景 | RFQ 首次短回复、邮件议价修订；不宣称已经接入平台 |
| 至少两轮对话迭代 | 第一轮补全询盘缺项；第二轮处理改量/交期要求，保留记录 |
| 两个相关工作流 | 首次回复与报价修订，共用目录、规则与报价版本 |
| 两类校验 | 平台相关性/信息完整性 + 合同/报价条款检查；平台当前规则需核实 |
| 两种反馈 | 文字批注与风险标记，另有版本对比 |
| 数据与知识实际调用 | 从目录和带来源的规则条目中检索，展示引用 |
| 实际 AI 调用 | 接口配置后现场真实生成；没有 API 时不能宣布参赛作品完成 |

无需先学完整外贸课程，但要逐项解释 MOQ（最小起订量）、币种、货品金额、报价有效期、备货与发货/到货的区别。知识随功能学习。

## 分阶段带做方式

一次一个小目标，每步先说明“做什么、为什么、改哪些地方”，再由助手处理代码与自测，给用户一个具体操作和预期现象。用户反馈后再进入下一步；不用一次抛完整技术栈、长命令串或多个待回答问题。

| 阶段 | 可见成果 | 用户学会什么 | 验收 |
|---|---|---|---|
| 0 已有工具检查 | 本地 JSON 校验页 | 启动、输入、校验与错误提示 | 用户亲自操作一遍；自动测试通过不代替用户体验 |
| 1 产品目录 | 页面显示模拟商品与价格 | 数据文件如何影响页面 | 修改一个商品名称并看到变化 |
| 2 确定性报价 | 输入数量、显示货品金额 | 输入→逻辑→输出，模型不负责算术 | 更改数量后金额符合目录档位 |
| 3 业务核对 | 缺项清单、规则来源、风险提示 | 数据校验与业务规则的区别 | 补全一项信息后对应提醒消失 |
| 4 AI 回复 | 基于资料生成英文客户草稿和中文内部清单 | 提示词、上下文、接口、返回结果 | 真实调用且没有编造目录事实 |
| 5 修订与导出 | 第二次修改、版本对比、下载 | 状态、关联工作流、文件输出 | 连续完成两轮迭代，旧版保留 |
| 6 完成比赛 | 可重启运行的作品及提交材料 | 测试、复现、讲解与收尾 | 三分钟演示与清单逐项核对 |

这是顺序，不是要求用户先学完 Python。已会的内容快速通过，卡住时只处理当前环节。具体正式编码时间范围仍依主办方规则；可以先理解流程与准备资料。

## 学习完成标准

用户不需要背框架 API，应能做到：
- 自己启动和停止作品。
- 修改商品资料、一个界面文案或一条提示词，并验证变化。
- 用自己的话说出“输入→查资料→生成/计算→检查→修改→输出”。
- 报错时保存错误原文、复现步骤和最近改动，交给 AI 协助定位。
- 知道模型输出不自动等于事实，价格由代码和明确资料控制。

之后再逐块解释主程序、数据模型、业务校验与接口模块。深入理解是后续持续目标，不把它变成首次参赛的先决条件。

## 成本、依赖与未解决问题

- 使用已验证 Streamlit/Pydantic；首版不加 Dify、复杂图数据库或多代理框架。
- 少量模拟目录直接使用 JSON；无需为首版安装文档解析和复杂检索平台。
- 评测先用现有 Python 测试与固定案例；有需要再用 Promptfoo。
- 不买域名、服务器或额外付费工具。免费/赞助模型是否可用仍需真实验证，不能承诺额度或可用性。
- 模型未接入时，可先完成界面、计算和检查，但必须明确只是本地阶段，不能把模板当 AI 演示。
- 平台规则来源、赛前编码范围与部分赛事时间冲突仍在 docs/competition-brief.md / docs/product-direction.md 中列为待确认。
- 10/31 21:00 前海报、11/1 13:00 作品提交；完整源码/README/配置/第三方声明、数据知识库说明、一页方案与三分钟演示都应纳入收尾，不只写代码。
